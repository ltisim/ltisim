# AI Grading Validation — Few-Shot Exemplars

This document records the validation results for the few-shot exemplars feature added to the AI evaluator in `backend/src/services/ai/scoring.js`. It's meant as a reference for future regression testing and for understanding how the feature behaves on real grading calls.

The grading design itself (zero-shot versus few-shot) is implemented in `backend/src/services/ai/scoring.js`. For instructor-facing guidance on when to use exemplars, see `docs/Product-Overview.md` → "AI Grading: Zero-Shot and Few-Shot".

---

## Methodology

The feature was validated using a Node script at `backend/src/utils/validate-exemplars.js` that grades synthetic transcripts against a real assignment (`#4 — Delivering Difficult Feedback`) in both zero-shot and few-shot modes, using real AWS Bedrock calls.

### Why synthetic data

The project has no human-graded student sessions to use as ground truth, so formal accuracy metrics (QWK, human agreement, MAE against a gold set) are not applicable. Instead, validation focuses on:

1. **Functional correctness** — does every new code path work end-to-end without errors?
2. **Mode differentiation** — does few-shot mode actually produce different prompts and outputs than zero-shot?
3. **Persistence round-trip** — do exemplars save to JSONB and read back with correct shape?
4. **Inter-run consistency** — at `temperature=0.1`, does the grader produce stable scores across repeated runs?

### Test data provenance

To avoid author-bias (where transcripts and exemplars written by the same author share implicit style cues that wash out the signal), the synthetic transcripts and exemplars were generated by a **different LLM** than the grader (Claude on Bedrock). This separates three parties: transcript author, exemplar author, and grader.

The test data lives inline in `validate-exemplars.js` under the `TRANSCRIPTS` and `EXEMPLARS` constants. Three transcripts at high/medium/low quality tiers, plus two exemplars on the "Active Listening" criterion only (one Excellent at 25 pts, one Not Met at 0 pts).

### Assignment used

- **#4 — Delivering Difficult Feedback**
- Type: `simulation`
- Max score: 100
- Rubric: 4 criteria × 25 pts each
  - Professionalism & Tone
  - Constructive Framing
  - Active Listening *(exemplars attached in few-shot runs)*
  - Action Planning
- 4 proficiency levels per criterion (Excellent / Good / Developing / Not Met)

### Run configuration

- 12 real Bedrock evaluation calls per run (~$0.10)
- 2 runs per transcript per mode (3 tiers × 2 modes × 2 runs)
- Grader: whatever AWS Bedrock model is configured on the assignment's `ai_provider_config`
- `temperature: 0.1` (unchanged from production)
- Single holistic evaluation call per session (not per-criterion — see "Architectural Note" at the end)

### Reproducing

```bash
cd /path/to/ltisim/backend
node src/utils/validate-exemplars.js
```

The script is idempotent: it writes exemplars to assignment #4, reads them back for verification, then restores the original rubric.

## Interpretation

### What the run proves

**The plumbing works end-to-end.**

1. Zero-shot mode preserves its prompt structure (no exemplar block, no regressions from existing assignments).
2. Few-shot mode injects exemplars correctly, bumps `max_tokens`, and extends the system prompt.
3. Per-criterion optionality works: exemplars on one criterion do not affect the others' prompt shape.
4. The grader **actually uses** exemplars in few-shot mode — its reasoning text references them by name.
5. Exemplars round-trip through JSONB persistence.
6. Inter-run consistency is strong at `temperature=0.1` (stdev ≈ 0 on most runs).
7. Chain-of-thought `reasoning` field is populated in both modes and stored on `score_breakdown.criteria_evaluations[].reasoning`.

### What the run does NOT prove

This validation is **functional**, not **accuracy-based**. Specifically:

- **No human ground truth.** We can't compute QWK, MAE, or human-agreement metrics without hand-graded sessions. The target scores in the transcript prompt ("~90/100 for high", etc.) were suggestions to the transcript-generator LLM, not ground truth.
- **Small sample.** 3 transcripts × 2 runs = 12 grading calls. Not enough to draw statistical conclusions about exemplar impact.
- **The grader already saturated the scale at the extremes.** High tier hit 100/100, low tier hit 0/0 in both modes — leaving no headroom for exemplars to move anything. Only the medium tier has room to differentiate, and we only tested one medium transcript.
- **No gradient in the exemplar criterion.** Active Listening scored identically in both modes across all tiers. That's because (a) the rubric language for this criterion is already concrete ("asks thoughtful questions, reflects back, validates feelings"), and (b) the high/medium/low transcripts are unambiguous on this dimension.

### What the numeric results suggest

The numeric lift from exemplars was small: +4 on one medium run, 0 elsewhere. **This is a meaningful finding, not a failure.**

When the rubric language is concrete and the transcript is unambiguous, zero-shot grading is already near-ceiling and exemplars have little room to improve anything. Exemplars exist for the *other* cases:

1. **Abstract rubric criteria** — "demonstrates critical thinking", "shows cultural awareness". These benefit most from concrete anchors.
2. **Grader uncertainty** — situations where two transcripts could plausibly score differently depending on interpretation.
3. **Non-obvious instructor standards** — when the instructor wants to steer the grader toward something that isn't fully captured in the rubric text.

This result **validates the design decision** to make exemplars optional and per-criterion. An instructor authoring an assignment like "Delivering Difficult Feedback" with already-concrete level descriptions doesn't need exemplars — and the feature correctly imposes no overhead in that case. An instructor who discovers the grader is struggling on one specific criterion can add exemplars just to that criterion without affecting the others.

### Expected conditions for larger few-shot lift

Future validation runs should try to construct test conditions that give exemplars room to matter:

- A rubric criterion with **intentionally abstract** level descriptions.
- **Medium-tier transcripts** that are genuinely ambiguous between two adjacent levels.
- **Multiple medium-tier transcripts** (5+) to average out run-to-run noise.
- **Exemplars that embody a non-obvious interpretation** of the rubric — e.g., an "Excellent" exemplar that rewards concise answers, when the rubric doesn't explicitly mention brevity.

Under those conditions, we would expect to see a clearer gap between zero-shot and few-shot scores, and the few-shot runs should cluster around the interpretation encoded in the exemplars.

## Architectural Note: Holistic vs. Per-Criterion Evaluation

Confirmed during this validation round that the evaluator remains **holistic** — one AI call per session, entire rubric evaluated in a single coherent pass. Specifically in `scoring.js`:

- `evaluateSession()` makes exactly one `provider.evaluate()` call per invocation.
- The prompt contains the full transcript, all rubric criteria with their levels, and all exemplars across all criteria, in a single message.
- The JSON response schema requests a single `criteria_evaluations: [...]` array covering every criterion at once.
- The grader's chain-of-thought `reasoning` is written for all criteria in the same response, so cross-criterion context is preserved.

The few-shot feature **did not fragment** this architecture. The exemplar block is injected into the single holistic prompt; it does not spawn per-criterion grading calls.

This preserves the design properties that matter:

- **Cross-criterion context is preserved.** When grading "Active Listening" the model already knows what it said about "Constructive Framing" in the same response — criteria can inform each other.
- **`overall_feedback` is grounded.** It's written alongside the per-criterion scores in the same output, not stitched together after N independent calls.
- **Exemplars stack correctly across modes.** When exemplars are attached to one criterion, the grader still sees the other three criteria's descriptions in the same prompt; exemplars anchor one dimension without collapsing the others into it.
- **Cost is 1× per session.** A per-criterion split on this rubric would quadruple Bedrock API calls for no accuracy benefit (and likely worse outputs due to lost context).

## Regrade Path (not exercised in Run 1)

Run 1 exercised `evaluateSession()` directly on synthetic transcripts and did not go through the regrade endpoints (`POST /admin/sessions/:id/regrade` or `POST /admin/assignments/:id/regrade-pending`). The regrade endpoints are thin wrappers that re-invoke the same `evaluateSession()` function with the current assignment rubric, so they inherit the same grading behavior validated here. The specific things worth validating on a future regrade-focused run:

1. **Released-session protection.** Attempt to regrade a released session → expect HTTP 400 with the "released sessions are frozen" message. Confirmed by code review but not by an HTTP call.
2. **Pending-review pathway.** Create a pending-review session, modify the rubric (add/remove exemplars), call the single-session regrade endpoint, and confirm that `score_breakdown.criteria_evaluations` reflects the new rubric (e.g., new `reasoning` text referencing any added exemplars) and `ai_evaluation.regraded_at` is populated.
3. **Bulk regrade** — seed 3+ pending-review sessions on an assignment, call `POST /admin/assignments/:id/regrade-pending`, confirm `{total, succeeded, failed}` counts match and each session's draft was updated.
4. **Bulk regrade partial failure.** Introduce a failure condition (e.g., an assignment whose `ai_provider_config` is invalid) and confirm the endpoint reports per-session errors without aborting the loop.

None of these were run in Run 1 because the project has no real pending-review sessions. They can be exercised by extending `backend/src/utils/validate-exemplars.js` to directly insert synthetic sessions via SQL before calling the regrade endpoints.

## How to extend this document

When running additional validation passes (e.g., after tuning prompts, switching models, or adding new test conditions), append a new `## Run N — YYYY-MM-DD` section below the existing runs rather than overwriting. This preserves a historical record of how the grader has behaved over time.

For each run, record at minimum:
- Date, assignment ID, grader model
- The four checks (prompt assembly, real grading results, sample reasoning, persistence)
- Any changes to the methodology or test data from the previous run
- An interpretation paragraph explaining what the numbers mean in context

The validation script (`backend/src/utils/validate-exemplars.js`) is self-contained and can be edited to swap in new transcripts, exemplars, or target criteria without changing the core logic.
